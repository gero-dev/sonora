# Поиск по мелодии и треку (распознавание)

> Статус: **Sonora 3.4.0+, модуль распознавания v2**. На экране поиска есть два
> режима, как в поиске Google по треку:
> 1. **«Слушать вокруг»** — приложение записывает 8 секунд звука и распознаёт
>    играющую песню;
> 2. **«Напеть мелодию»** — hum-to-search: 10 секунд напетой/просвистанной
>    мелодии сравниваются с треками на устройстве.
>
> Распознавание, фоновое обогащение и проверка работают в фоне
> (`Dispatchers.IO`), воспроизведение не прерывается, интерфейс не блокируется.

## Как это работает

### 1. Запись

`FragmentRecorder` — `AudioRecord`, 16 кГц, моно, PCM 16 бит, 8 с («слушать
вокруг») или 10 с («напеть»), на `Dispatchers.IO`. Разрешение `RECORD_AUDIO`
запрашивается через системный диалог. Для ручной проверки без микрофона можно
импортировать аудиофайл («Из файла»).

### 2. Распознавание: «Слушать вокруг»

Порядок:

1. **Кэш результатов по хэшу отпечатка** — SHA-256 от кадров/пиков/RMS.
   Повторный фрагмент (или тот же файл) не ходит в сеть. TTL 30 дней.
2. **AudD**, если в настройках модуля задан ключ: multipart-запрос
   `https://api.audd.io/` возвращает title/artist/album/artwork.
3. Если ключа нет, AudD не нашёл или сеть недоступна — **честный офлайн-fallback**:
   сверка фрагмента с отпечатками локальной фонотеки (до 200 треков, ленивый
   индекс в `fingerprint_cache_v2.json`). Работает только для песен, которые уже
   есть на устройстве.

### 3. Улучшенный офлайн-отпечаток (v2)

Вместо 12 «приращений энергии» используется схема spectral peak picking +
constellation hash:

| Шаг | Параметры |
|---|---|
| Кадры | 64 мс (1024 сэмпла), шаг 32 мс — перекрытие 75 % |
| Частоты | 48 лог-полос, 100–5500 Гц |
| Пики | до 5 локальных максимумов на кадр, не ниже −26 дБ от самого громкого пика кадра; кадры тише −90 дБ считаются тишиной |
| Пары | «якорный пик → до 4 пиков в следующих 8 кадрах» → 16-битный хэш |
| Поиск смещения | голосование по инвертированному индексу хэшей (как в Shazam) |
| Оценка | `0.40 × доля совпавших пар + 0.50 × F1 пиков (допуск ±1 полоса) + 0.10 × покрытие` |
| Порог | `FingerprintMatch.MIN_SCORE = 0.50`; уверенно — `0.70` |

Почему так:
- **Несколько перекрывающихся окон** дают устойчивость к сдвигу фрагмента;
- **пики по динамике кадра** переносят шум/эквалайзер/громкость: шум поднимает
  «пол», но не меняет взаимное расположение громких пиков;
- **допуск ±1 лог-полоса и ±1 кадр** прощает микрофонные искажения;
- **пары пиков** резко уменьшают ложные совпадения по сравнению с одиночными
  пиками;
- **F1 (precision/recall)** не даёт короткому фрагменту «набрать» оценку на
  нескольких случайных пиках.

Возвращается **top-N кандидатов** с оценкой; лучший сразу можно слушать, если он
есть в фонотеке. На синтетике: та же запись с шумом даёт 0.75–1.0, разные
записи — ниже 0.35.

### 4. Распознавание: «Напеть мелодию» (hum-to-search)

1. **Pitch tracking** — YIN (нормированная разностная функция, порог
   апериодичности 0.10, уточнение периода по минимуму разности): 8 кГц, окно
   64 мс, шаг 25 мс, диапазон 70–1100 Гц.
2. **Мелодический контур** — частота → MIDI-полутоны, медианный фильтр (окно 5),
   обрезка невокализованных краёв, нормировка по медиане (транспонирование не
   влияет). Контур пригоден, если ≥ 10 вокализованных кадров, ≥ 25 % кадров и
   ≥ 1.5 с.
3. **DTW** (Dynamic Time Warping) — сравнение контуров с полосой Сакое–Чибы:
   устойчиво к другому темпу; стоимость кадра: `|Δполутон|` (≤ 4), штраф за
   невокализованный кадр 3.0. Похожесть нормируется в 0..1, порог
   `MelodyMatcher.MIN_SCORE = 0.72`.
4. **Контуры фонотеки** считаются лениво по первым ~20 с файла (до 80 треков) и
   кэшируются в `melody_contours_v2.json`.

Честное ограничение: hum-режим работает **только по трекам на устройстве** —
у стриминговых треков нет локального аудио для анализа. Интерфейс пишет это
явно. На синтетике top-1 верный при транспонировании, смене темпа ±30 % и шуме.

### 5. Фоновая проверка и обогащение (после показа результата)

Результат публикуется сразу, а отдельная отменяемая корутина (`Dispatchers.IO`)
доделывает:

1. **сверку с фонотекой** — 5–10 с фрагмента против локальных отпечатков,
   топ-4 совпадения добавляются в «Другие варианты»;
2. **проверку кандидата по аудио** — если телеметрия включена и у онлайн-кандидата
   есть видео-id: существующий сниппет-резолвер yt-dlp скачивает **короткий
   сниппет (8 с)**, `LocalPcmDecoder` декодирует, отпечаток сверяется с
   фрагментом. Полные треки не скачиваются;
3. **аудио-фичи ReccoBeats** для лучшего кандидата (сеть + кэш) — подпись
   «124 BPM · энергия 82 %».

Гарантии безопасности:
- всё на `Dispatchers.IO`, UI-поток свободен;
- жёсткие таймауты на каждый шаг, отмена через `RecognitionController.cancel()`;
- фоновая проверка **не трогает ExoPlayer, аудио-фокус и историю прослушиваний**
  — это отдельные вызовы yt-dlp/MediaCodec/ReccoBeats;
- семафор на 2 параллельных анализа ReccoBeats и пауза ≥ 1 с между сетевыми
  запросами (бережём публичный API);
- ошибки/офлайн/выключенная телеметрия не ломают результат — просто нет
  дополнительных данных.

### 6. Ранжирование результатов поиска

`data/telemetry/SearchRanking.kt` переранжирует список результатов:

```
score = соответствие тексту (название/исполнитель/альбом, точное совпадение)
      + 0.18, если трек уже на устройстве
      + 0.30 × уверенность распознавания (если трек пришёл из распознавания)
      + небольшой бонус за полноту аудио-фич
```

Поэтому после «поиска по мелодии» распознанный трек оказывается наверху, а
локальная копия — выше стримингового дубля.

## Кэши и версии форматов

| Файл в `filesDir` | Что хранит | Версия |
|---|---|---|
| `fingerprint_cache_v2.json` | пики отпечатков локальной фонотеки (Base64) | 2 |
| `melody_contours_v2.json` | мелодические контуры локальной фонотеки | 2 |
| `recognition_results_v1.json` | результаты распознавания по SHA-256 отпечатка | 1 |

Формат отпечатков версионирован. Старый файл `recognition_fingerprints.json`
(v1) **не читается и не удаляется**: он просто игнорируется, а отпечатки
пересчитываются в новом формате (одноразовое «переиндексирование» в фоне).

## Что выбрать: AudD, локальный отпечаток, напев

| | AudD | Локальный отпечаток | Напев (DTW) |
|---|---|---|---|
| Что находит | любую песню из базы AudD | только файлы своей фонотеки | только файлы своей фонотеки |
| Нужен ключ | да (300 бесплатных) | нет | нет |
| Точность | высокая | высокая для своей фонотеки | средняя (зависит от того, как поют) |
| Приватность | фрагмент уходит на api.audd.io | всё на устройстве | всё на устройстве |

Ключ AudD вводится в панели распознавания и хранится в отдельных prefs модуля
(`sonora_recognition`), не в общих настройках.

## Ограничения

- Офлайн-отпечаток — эвристика: распознаёт только свою фонотеку, возможны
  ложные срабатывания при очень похожих записях (ремиксы, live-версии).
- Первый проход локального индекса может занять минуты (декодирование до 200
  файлов через MediaExtractor/MediaCodec). Процесс в фоне, отменяемый, с
  прогрессом «Сверяем с фонотекой: X из Y».
- Мелодийный индекс ограничен 80 треками и первыми ~20 с каждого файла
  (декодирование + pitch tracking). Далее работа идёт из кэша.
- Инструментальные треки с плотным аккомпанементом распознаются по напеву хуже
  вокала: DTW сравнивает контуры, а не тембр.
- Проверка кандидата сниппетом требует yt-dlp/ffmpeg и сети; без них проверка
  честно пропускается.
- Нет обработки после смерти процесса (осознанно: без foreground-сервиса).

## Файлы

`data/recognition/`:

- `RecognitionController.kt` — пайплайн, состояния, кэш, отмена;
- `RecognitionModels.kt` — режимы, фазы, результат, альтернативы, верификация;
- `AudioFingerprint.kt` — отпечаток v2, индекс, top-N (`AudioFingerprintSearch`);
- `LocalLibraryFingerprintIndex.kt` — сверка с фонотекой, `fingerprint_cache_v2.json`;
- `PitchTracker.kt`, `MelodyContour.kt`, `MelodyMatcher.kt` — hum-to-search;
- `LocalLibraryMelodyIndex.kt` — контуры фонотеки, `melody_contours_v2.json`;
- `RecognitionResultCache.kt` — кэш результатов по хэшу отпечатка;
- `RecognitionVerifier.kt` — фоновая проверка (фонотека, сниппет, фичи);
- `RecognitionEnricher.kt` — метаданные + кандидаты;
- `AudDClient.kt`, `FragmentRecorder.kt`, `Pcm.kt`, `LocalPcmDecoder.kt`,
  `RecognitionSettings.kt`.

`data/telemetry/`: `SearchRanking.kt` (переранжирование), `AudioFeatureRepository.kt`
(лимиты параллелизма/рейт-лимит), `AudioFeature.kt` (`confidence`).

UI — `ui/screens/SearchScreen.kt`. Тесты — `app/src/test/java/app/sonora/data/recognition/`:
`AudioFingerprintTest`, `MelodyMatcherTest`, `SearchRankingTest`, `PcmTest`,
`AudDResponseParserTest`.

## Как проверить вручную

1. **«Слушать вокруг» без ключа**: проиграйте трек из своей фонотеки рядом с
   телефоном → «Найти по фрагменту». Ожидаемо: статусы «Запись фрагмента» →
   «Поиск по фонотеке» → карточка с процентом, кнопкой «Слушать» и вариантами.
2. **С шумом**: то же при тише играющей музыке/фоновом шуме — результат должен
   остаться, процент может снизиться.
3. **AudD**: добавьте ключ → «Найти по фрагменту» на незнакомую песню. Ожидаемо:
   карточка AudD, затем «Ищем информацию…» (обогащение) и «Проверяем совпадение
   в фоне…» (локальная копия/сниппет/фичи). Плеер не должен прерываться.
4. **«Напеть мелодию»**: включите режим «Напеть мелодию», напойте припев знакомого
   локального трека 10 с. Ожидаемо: статусы «Разбираем напетую мелодию…» →
   «Сверяем мелодию: X из Y» → карточка с процентом и «Слушать». Для
   стримингового трека — подсказка, что напев ищет только по устройству.
5. **Отмена/поведение в фоне**: во время проверки нажмите «Отмена»/«Закрыть» —
   проверка прекращается; уход с экрана поиска не отменяет распознавание.
6. **Кэш**: повторите тот же импорт файла («Из файла») — второй раз карточка
   появляется сразу с пометкой «Результат из кэша — сеть не использовалась».
7. **Офлайн**: включите авиарежим — «Слушать вокруг» без ключа и «Напеть» должны
   работать по фонотеке, ошибок сети быть не должно.
8. **Телеметрия**: Настройки → выключите телеметрию аудио → проверка кандидата
   сниппетом и аудио-фичи пропускаются, результат и локальная сверка остаются.
